# 客服 Agent 设计文档

> 一套接 QQ 的客服 Agent 系统：客户提问 → 客服 Agent 查知识库作答 → 答不了就转运维 → 人工可随时接管。
> 以插件形式跑在 DeepSeek Harness 上，不改框架源码。

**怎么用这份文档**：第 0 节是 30 秒版本（面试开场直接说）；第 1–5 节按模块讲设计；第 6 节知识库给了**通俗版**和**专业版**两套讲法（对着不懂的人讲通俗版，对着懂的人切专业版）；第 7 节评测；第 8 节结构图；第 9 节高频追问；第 10 节主动交代局限。

---

## 0. 30 秒概览

**一句话**：一个跑在 DeepSeek Harness 上的客服 Agent，接 QQ，带知识库检索、人工接管、运维转交，作为插件分发。

**三个角色，两条边界**：

```
客户  ⇄  客服 Agent  ⇄  运维 Agent
        （可互相转交）    （客户永远碰不到）
```

- 客服 Agent 面向客户，只答得了问题，查不了后台、看不到账单和容器。
- 运维 Agent 只和内部人以及客服 Agent 对话，客户的消息永远进不到它这里。
- 知识库两边都能读，但客服读不到内部字段。

**六个关键取舍**（每个后面都有一节展开）：

| 取舍 | 选择 | 一句话理由 |
|---|---|---|
| 怎么加功能 | 插件 + 预设，不改框架 | 装上去就能用，别人也能装 |
| 消息怎么存 | append-only 的 jsonl 追加日志 | 可重放、可审计、坏只坏尾巴 |
| 会话怎么分 | 私聊一人一条、群聊一群一条 | 这是产品语义，不是配置 |
| 图片怎么处理 | 落盘 + 按需 OCR，主模型纯文本 | 省钱、可审计、主模型可换 |
| 知识库长什么样 | 一张张"故障卡片"，不是文档库 | 客服要的是"这句话我该回什么" |
| 答不准怎么办 | 三级判定，判不准就追问 | 客服系统最怕的不是不会，是编 |

**规模**：5 个工具、15 条知识库条目、507 项自动化检查、12 条端到端评测、26 条检索评测。

## 1. 提示词设计：三层，不是一个大 prompt

### 1.1 三层各写什么

**第一层 · 身份与边界**

你是谁、支持什么产品、什么绝对不能说。比如：你支持的是某款托管服务；不要向客户暴露内部服务名、集群名、节点名、内部系统地址、知识库条目编号。

这一层回答的是"**你是谁、你不是谁**"。

**第二层 · 处理流程**

把客服的判断过程写成可执行的步骤，而不是口号：

1. 客户说什么，先检索知识库。
2. 按检索给出的置信度分三种情况处理：证据够就直接答；只是"像"就先确认；没找到就追问。
3. 需要查后台、账单、容器、日志时，转交运维；转交前先把账号标识、错误原文、发生时间收集齐。
4. 客户确认问题解决后，把这次的错误特征和解决办法沉淀成候选条目。

这一层回答的是"**遇到情况按什么顺序做判断**"。

**第三层 · 表达方式**

不旁白内部过程（不说"我先查一下知识库"）、不承诺做不到的事（不说"我帮你查"）、一条消息只推进一个问题、用客户听得懂的话、不确定就说不确定。

这一层回答的是"**话怎么说**"。

### 1.2 为什么不用一个大 prompt

三层混在一起有四个具体问题，都是我实际遇到的：

**第一，失效方式不同，但改动会互相干扰。**
身份写坏了，表现是"答错产品"；流程写坏了，表现是"该追问的时候瞎编方案"；表达写坏了，表现是"话很客气但什么也没答"。混成一段，你改任何一处都不知道会伤到哪一处。

真实例子：客户问"海外模型支持吗"，我收紧"不要假装去查数据"这条规则后，模型改用"token 量"这种实现术语绕开——**同一条约束的两个侧面**，分开写才改得动。

**第二，长度会吃掉优先级。**
一个几千字的 prompt，模型对中间部分的注意力最弱。三层分开、每层短，关键约束才落在模型的注意力范围内。

**第三，可测试性。**
分层的直接好处是"评测能定位到层"。12 条端到端评测里，6 类泄漏检查（实现细节 / 条目编号 / 检索旁白 / 错误承诺 / 平台术语 / URL）分别对应第三层；"该不该答"对应第二层。混写了，你只能看到"整体变差了"。

**第四，复用。**
同一套流程层能配不同身份层（换产品只改第一层）。

### 1.3 运行时变量与版本固化

- 产品名、知识库路径这类东西是**占位符**，会话创建时注入，不写死在 prompt 里。
- 有个坑：预设里的 `prefix` 默认只追加在框架内置规范后面，要完整生效得显式声明"完整模式"，否则你会看到变量没有值的报错（`prompt variable "..." has no value`）。
- **预设是会话创建时固化的版本**。改了 prompt，老会话继续跑旧版，只有新会话用新版。这是特性（会话可重现），不是 bug，但不知道就会误判成"改了没生效"。

### 1.4 踩的坑（面试必讲）

**把"向用户提问"的工具放进了客服预设。**

那是个交互式工具：模型调用它，界面弹问题，等人点。但渠道场景（QQ）没有人点按钮，于是整轮直接中断，**客户收不到任何回复**。

- 现象：机器人偶发不回复，日志里有 `ASK_ABORTED`。
- 结论：**无头渠道的 Agent，工具集里不能有阻塞式交互工具。** 需要追问就用普通文本追问。

**兜底**：任何非正常结束的回合，网关补一句固定话术，宁可说"抱歉，能再说一次吗"，也不能让客户等到超时窗口过期。

## 2. 工具设计

### 2.1 五个工具

| 工具 | 干什么 | 为什么必须有 |
|---|---|---|
| `kb_search` | 用客户的话检索知识库，返回"敢不敢直接答"的结论 + 候选条目摘要 | 系统里唯一的"对外知识"入口 |
| `kb_get` | 取某一条的完整内容 | 摘要不够答细节时用 |
| `kb_propose` | 把刚解决的问题写成候选条目 | 让知识库能长大 |
| `ocr_image` | 客户发的截图 → 文字 | 客户报错第一反应就是截图 |
| `ops_handoff` | 需要查后台/集群时转给运维 | 客服没有后台权限，必须有人接 |

### 2.2 设计原则

**少而正交。** 五个工具对应流程里的五个决策点。多一个工具，模型就多一次选错的机会——工具选择错误是 Agent 最常见的失败模式，比工具本身出错更常见。

**输出格式是硬契约。** 返回值必须严格匹配声明的 schema，宿主在模型看到结果之前逐字段校验（`additionalProperties: false`，多一个字段就是硬错误）。这条我付出过真实代价，见 2.3。

**置信度在工具里内建。** `kb_search` 不只返回条目，还返回 `verdict`（`direct` / `reference` / `miss`）、`confidence`、`margin`、以及 `clarify[]`（该问客户什么）。**把"该不该答"从模型的自由判断变成结构化信号**——这是整个系统里最关键的一个设计决定。

**权限在工具层做，不在提示词层求。**
客服角色检索到的条目，内部字段（根因、内部处置步骤、验证方法）在返回前就被摘掉了；`kb_propose` 的 `audience: internal` 对客服角色**直接报错**，而不是"劝他别用"。提示词是建议，代码是约束。

**参数越窄越安全。**
图片工具只接受一个路径参数，且限制在图片目录内，防路径穿越。工具参数越少，模型填错的概率越低，攻击面也越小。

### 2.3 踩的坑（面试必讲）

**工具输出多了一个字段，模型就"客气地什么也不答"。**

我给检索结果加了两个诊断字段（`signals` 各信号取值、`margin` 前两名分差），用来调参。**忘了同步输出 schema**。结果：

```
tool "kb_search" returned invalid output:
  "value.hits[0].signals" is not a declared property (additionalProperties: false)
  "value.margin" is not a declared property (additionalProperties: false)
```

宿主拒收，模型拿不到任何检索结果，于是回头向客户要信息——**语气完美，内容为零**。

更难受的是：507 项测试全绿。因为我的检索单测直接调检索函数，绕过了工具层。这个教训放到第 7 节讲。

修复不只是补两个字段，还加了一条**驱动真实工具调用、再按声明的 schema 校验返回值**的测试，并且包含两条负向用例（故意多塞一个字段、故意缺必填，必须报错）——否则这个校验器自己坏了也没人发现。

## 3. 消息持久化：jsonl 追加日志 + key 映射

### 3.1 存的是什么

**每个会话一个文件，一行一条事件，只追加、不改写。**

```
session.v4.jsonl.zstd
├─ 第 1 行：会话头（工作区、创建时间、预设版本）
├─ 第 2 行：客户消息
├─ 第 3 行：模型思考
├─ 第 4 行：工具调用 + 工具结果
├─ 第 5 行：模型回复
└─ ...
```

压缩成多帧 zstd，追加时只写新帧，读取时逐帧解。

**为什么是追加日志，不是数据库**：

- **可重放**：出问题可以把整段对话重新喂回去复现。
- **可审计**：客户投诉"你昨天说会退款"，日志里有一字不差的原话。
- **单写者、单机**：不需要事务、不需要并发控制，一个文件锁就够。
- **坏了只坏尾巴**：文件末尾损坏，前面的历史照样能读。

**关键认知（面试官会认可这点）**：**日志是事实，模型看到的历史是视图。** 模型上下文里的消息是每次从日志里派生出来的，压缩、裁剪、重新组装都发生在"视图"层，不改日志本身。所以"上下文压缩"永远不会丢历史。

### 3.2 为什么要有 key → sessionId 映射（重点）

系统里有两个身份：

| | key | sessionId |
|---|---|---|
| 是什么 | **渠道身份**：谁在哪儿问的 | **运行时身份**：一个会话文件 |
| 例子 | `qq:group:123456`、`qq:8A3F...` | `chan-63c20d83-...` |
| 生命周期 | 跟着客户/群，长期不变 | 可能被重建、迁移、换模型 |
| 谁生成 | 我们的路由逻辑 | 运行时 |

**为什么要多这一层，而不是直接拿客户 ID 当文件名：**

1. **不同渠道会撞名。** QQ 的 openid 和微信的 openid 是两套编号体系，直接当文件名迟早冲突。加渠道前缀能解决撞名，但渠道一多，文件名规则就开始长毛。
2. **会话要能重建而客户无感。** 预设升级、模型更换、目录迁移，都会产生新会话，但客户还是那个客户。映射层让"换会话"对客户透明。
3. **不把客户标识散落到文件系统里。** 文件名是随机会话 ID，客户 ID 只存在映射表里，日志目录就算被看到也不直接暴露身份。
4. **一个客户可以有多个会话。** 比如"当前会话"和"上次那个问题"，映射层是"多对一"的天然位置。

**代价（一定要讲，讲代价才显得真做过）**：两层身份就可能不一致。

真实事故：清理脚本删了会话文件，但没删映射。之后客户再发消息 → 映射指向一个不存在的会话 → 恢复失败 → **消息进来了却回不出去，而且不报错，只是静默不回**。

补救有三条：

- **自愈**：恢复失败时丢掉坏映射、新建会话，并且**保留原来的路由信息**（否则兜底回复会因为拿不到群号而发不出去）。
- **对账**：一个脚本定期对比"映射表"和"实际会话目录"，列出孤儿会话和坏映射。
- **删除语义**：删除只摘映射 + 从工作区摘出，**不删文件**。删文件会让界面报 ENOENT，会话还会被挪进"未分组"。

### 3.3 读取的坑

多帧 zstd，**只解第一帧就会"只读到 10% 的历史"**。这个 bug 的表现是"面板上只能看到前几条消息"，很容易误判成前端问题。

## 4. 会话分类（session 粒度）

### 4.1 物理隔离：四个工作区

```
私聊会话 / 群聊会话 / 评测会话 / 运维会话
```

**一条铁律：测试永远不能写进客户的会话目录。**

我最早把所有会话都写在开发工作区，结果开发工作区里堆了 46 个测试会话，被要求返工。现在的做法是：**按"会话等级"分目录**，评测再单独一个目录，且评测跑完自动清理。

### 4.2 逻辑粒度：这才是产品语义

| 场景 | 粒度 | key |
|---|---|---|
| 私聊 | 一人一条 | `<渠道>:<用户>` |
| 群聊（默认） | **一群一条** | `<渠道>:group:<群号>` |
| 群聊（可选） | 一人一条 | `<渠道>:<群号>:<用户>` |

**为什么群聊默认一群一条**：群里大家能看到彼此的对话，客服如果对每个人独立记忆，会出现"A 说了问题，B 追问，客服装作没听过"的割裂感。

**为什么又要能切成一人一条**：有些群是"多租户"用法（一个人一个客户），共用上下文反而会串号。

**这不是配置差异，是产品语义差异**——同一个技术实现，两种产品定义。

### 4.3 归属问题

群消息里要标明是谁说的，否则客服没法回答"你"是谁。做法是内容前加 `[群成员 昵称]` 前缀；这个前缀**只用于展示**，存历史时剥掉，避免污染检索和模型理解。

### 4.4 生命周期

| 动作 | 含义 | 群聊 | 私聊 |
|---|---|---|---|
| 归档 | 打标记 + 移出列表，客户再来自动恢复 | 3 天 | 30 天 |
| 清除 | 真删 | 30 天 | 90 天 |

**人工接管中的会话永远跳过清理**——那是正在处理的事，删了就是事故。

## 5. 图片处理（简要）

**做法**：主模型保持纯文本；图片先落盘，需要时调 `ocr_image` 拿文字。

**为什么不用多模态模型直接看图**：

- 成本：每张图都要过一遍视觉模型；
- 可审计：原图和识别文本都留着，出问题能核对；
- 可替换：主模型换了不影响图片链路。

**双后端**：macOS 自带 Vision（快且准，走 Swift 调用）和 tesseract（跨平台）。配置里可以指定，也可以自动挑。

**一个坑**：透明背景的 PNG 直接识别返回空。得先把图铺到白底上、转成标准色彩空间再识别。

**安全**：工具只接受路径，且校验必须落在图片目录内。

## 6. 知识库与检索

> 这一节给两套讲法。**6.1 通俗版**：完全不懂检索的人也能听懂，面试先用它铺垫。**6.2 专业版**：对方懂行时切过去，直接讲结构和参数。

### 6.1 通俗版：知识库是"故障卡片"，不是文档

#### 它长什么样

不是存一堆文档让人去读，而是**一张张卡片**。每张卡片回答六个问题：

1. **客户会怎么描述这个错？**（错误特征：报错原文、错误码、关键词）
2. **实际看到的现象是什么？**
3. **能对客户说的原话是什么？**
4. **根本原因是什么？**（内部看）
5. **怎么修的？**（内部看）
6. **怎么确认修好了？**

#### 为什么切成卡片

因为客服要做的事是"**客户说了这句话，我现在该回什么**"，不是"读一篇三千字的文档"。

一篇文档里，一段话可能同时包含"现象""原因""历史背景"，检索到它你也说不清该信哪部分。切成卡片、每张卡片再按字段拆开，就能精确到"客户这句话命中的是这张卡片的**错误特征**"——这是最强的证据。

#### 怎么找（用图书馆打比方）

客户说了一句话，系统要做三件事：

**第一步：两路同时找。**

- 一路**按字面找**：客户说"扣了 9.9 元"，卡片上就写着"9.9"，直接命中。这叫关键词检索。
- 一路**按意思找**：客户说"钱莫名其妙少了"，字面上跟"扣费"不重合，但意思接近。这靠把每段文字转成一串数字（向量），比数字的接近程度。

**第二步：把两路的结果合成一个排名。**

问题是两路的分数没法直接比（一个是关键词命中次数算出来的，一个是向量距离算出来的）。**解决办法是不比分数、比名次**：某张卡片在字面榜里排第 2、在意思榜里排第 5，就按名次算个综合分。好处是不用调参数，也不会因为某一路分数虚高就霸榜。

**第三步：打分，决定"敢不敢直接答"。**

综合分由几样东西加权算出来，最重要的是**错误特征有没有命中**——客户要是把报错原文贴过来了，那基本就是它了。其次是关键词覆盖了多少、这条历史上出现过几次。

最后落到三种结论：

| 结论 | 含义 | 客服该做什么 |
|---|---|---|
| **direct**（可以直接答） | 证据够硬 | 按卡片的"对客户说的话"回答 |
| **reference**（只能当线索） | 像，但不确定 | 先向客户确认一两个关键点，别直接下结论 |
| **miss**（没找到） | 知识库里没有 | **必须追问，禁止编方案** |

**为什么要分三级，而不是"找到就答、没找到就说不知道"**：因为现实里大量情况是"有点像"。直接答会答错，直接说不知道又太笨。中间这一级是客服系统的价值所在。

#### 两个"闸门"的故事（讲这个最有说服力）

**故事一：打印机 → 网关。**

有人问"打印机连不上"。系统答成了"网关 token 过期了"——完全不相干。原因是"按意思找"那一路，把两条都含有"连接失败"描述的东西算成了相似。

修法：加一道**证据闸门**——只有错误特征命中、或者关键词覆盖率达到一定比例，才算数；纯靠"意思相近"捞上来的，不足以当答案。

**故事二："服务有点慢" → 一个具体的扩缩容方案。**

有人抱怨"服务有点慢"。系统直接给出了"把副本数从 0 调到 2"这种具体操作。原因只是两边都有"服务"两个字，覆盖率刚刚够。

修法：加一道**覆盖闸门**——只共用一个泛词（服务、失败、异常这类），不许直接答，降级成"追问"。

**这两道闸门都不是设计出来的，是被真实误答逼出来的。** 这是我最想在面试里讲的部分：参数不是拍脑袋定的，每一条背后都有一个具体的错误案例。

#### 新问题怎么进库（闭环）

```
客户问题解决
   ↓
写成"候选"卡片（不进检索结果）
   ↓
人工审核：确认 → 转正 / 驳回
   ↓
去重：错误特征高度重合 → 并入老卡片，只把"出现过几次"加一
   ↓
失效：方案过时 → 标记失效（可查、但不参与检索）
```

去重这一步很重要：同一个错误被 20 个客户报过，不应该变成 20 张卡片，而应该是 1 张卡片 + "出现过 20 次"。**出现次数还会反过来影响排序**——反复出现的问题排在前面，但做了对数压缩并设上限，防止老卡片永久霸榜。

### 6.2 专业版：结构、双路召回与三级判定

#### 6.2.1 条目结构：事故形状（incident-shaped）

```jsonc
{
  "id": "subscription-fee-9-9-19-9",
  "title": "余额莫名扣减 9.9 / 19.9 元：订阅费",
  "status": "verified",            // verified | stale | deprecated | candidate
  "audience": "customer",          // customer | ops | internal
  "errorSignatures": ["9.9", "扣费", "余额少了"],  // 强证据字段
  "services": ["sophclaw"],
  "environments": ["prod"],
  "symptom": "客户发现余额少了 9.9 或 19.9 元…",
  "customerReply": "这 9.9 元是订阅费用，首月 9.9，次月 19.9…",  // 可对客户原文
  "rootCause": "自动续费订阅…",
  "resolution": "1. … 2. …",
  "verification": "账单明细出现订阅扣费记录…",
  "tags": ["billing", "subscription"],
  "updated": "2026-10-20"
}
```

四个要点：

1. **`errorSignatures` 是强证据字段**，专门装"客户可能原样贴过来的东西"：报错原文、错误码、精确金额、界面文案。检索里它的权重最高。
2. **`customerReply` 是可对外原文**，和内部的 `rootCause`/`resolution` 物理分开。客服角色读不到后两者——这条在工具层强制执行。
3. **`audience` 决定可见性**：`customer` 客服可直接答；`ops` 客服能答但只能按 `customerReply` 说，内部字段被摘掉；`internal` 客服完全不可见。
4. **`status` 有生命周期**：`verified` / `stale` / `deprecated` / `candidate`。只有 `verified` 和 `stale` 参与检索（`stale` 权重打折），`candidate` 和 `deprecated` 完全不进检索结果，但 `deprecated` 仍可被 `kb_get` 按 id 查到（便于追溯"以前是这么处理的"）。

#### 6.2.2 分块索引：字段级 chunking + 字段权重

一条条目被拆成 7 个块，每块独立建索引，**且带字段权重**：

| 块 | 来源字段 | 权重 | 理由 |
|---|---|---|---|
| `signature` | `errorSignatures` | **1.5** | 客户原样贴报错时，这是最强证据 |
| `title` | `title` | 1.3 | 标题是人工提炼过的浓缩语义 |
| `symptom` | `symptom` | 1.2 | 现象描述，客户口语最接近这里 |
| `customerReply` | `customerReply` | 1.1 | 对外话术，常含客户能看到的界面词 |
| `resolution` | `resolution` | 1.0 | 处置步骤 |
| `verification` | `verification` | 0.7 | 验证描述容易混入无关技术词，压低 |
| `meta` | `services` + `tags` | 0.6 | 服务名/标签是辅助信号 |

**为什么权重不同**：同一个词出现在不同字段，证据强度差一个量级。"磁盘占用"出现在 `verification`（"确认磁盘占用回落"）里，说明的是"怎么验证"，而不是"这个问题是磁盘占用"。**我最初不分权重，结果"查看我的磁盘占用"被"PVC 磁盘满"抢走了**——后者只在验证段提到了磁盘占用。

块级命中后，一条条目的得分取**它最强的那个块**（`score × weight`），其余块作为次要证据保留。

#### 6.2.3 双路召回

**词法路：BM25**

标准 BM25，`k1 = 1.2`、`b = 0.75`，按块建倒排索引（只遍历命中的 posting，不扫全库）。中文没有现成分词器，用了自己的切分：中文按二元/三元字组、英文按词、数字整体保留。

**语义路：向量**

默认后端是**特征哈希**（feature hashing）：把文本切成"词 token + 字符三元组"，用双哈希（一个定维度位置、一个定符号）投影到 512 维，再 L2 归一。

- 好处：零依赖、离线可跑、确定性（同样的文本永远同样的向量，可缓存、可复现）。
- 代价：**它不理解同义词**。"钱少了"和"扣费"在哈希空间里并不接近。所以语义路在这个系统里是**补充**，不是主力——主力是 BM25 + 错误特征。

另有一个 `http` 后端，接 OpenAI 兼容的 `/embeddings` 端点，带磁盘缓存（按 `sha256(text)` 存）和超时；失败时按配置降级回哈希向量并打 warning。所以**换真 embedding 只改配置**。

**融合：RRF（Reciprocal Rank Fusion）**

```
rrf(entry) = Σ_channel  1 / (K + rank_channel(entry))      K = 60
```

同一条目如果在两路里都出现，两个名次都计分（从第二次出现开始做去重修正，避免同一路里多个块重复刷分）。

**为什么用 RRF 而不是加权分数和**：两路分数量纲完全不同——BM25 是 TF-IDF 加权和，向量是余弦相似度（0–1）。做归一化要估计分布，换个知识库就得重调。**RRF 只看名次，天然免归一化**，这是它在这类系统里被广泛采用的原因。

#### 6.2.4 特征打分

融合后取前 N 条，为每条算一个最终分：

```
final = ( 0.46·relevance
        + 0.32·signature
        + 0.22·coverage
        + 0.20·signatureTokens
        + 0.06·prior )  × statusFactor
```

| 特征 | 含义 | 备注 |
|---|---|---|
| `relevance` | RRF 归一化后的名次相关度 | 主体信号 |
| `signature` | 整条错误特征是否被完整命中 | 0/1，最强单项 |
| `coverage` | 查询词被条目覆盖的比例 | 防"只共用一个词" |
| `signatureTokens` | 查询词落在错误特征字段内的比例 | 我后加的信号，解决"泛词抢答" |
| `prior` | 历史出现次数，`log1p` 压缩，10 次封顶 | 高频问题前置，但不许霸榜 |
| `statusFactor` | `verified`=1.0、`stale`=0.75、其它=0.6 | 过期方案降权 |

`signatureTokens` 的由来值得单说：**"查看我的磁盘占用"被"PVC 磁盘满"抢走**，因为后者的 `verification` 里写了"磁盘占用回落"。加了这个信号（查询词有多少落在 `errorSignatures` 里）之后，正确的条目 0.64 vs 错误条目 0.55，纠正了排序。**这个信号本质上是"证据在不在该在的地方"。**

#### 6.2.5 三级判定与两道闸门

```
if (score >= 0.30)                              verdict = reference
if (score >= 0.56 && margin >= 0.08
    && (signature || coverage >= 0.30))         verdict = direct
if (signature && score >= 0.56 - 0.12)          verdict = direct   // 客户贴了精确标识
```

- `margin >= 0.08`：**前两名分差**。两条分数接近时不许直接答——说明检索自己都没分清。
- `coverage >= 0.30`：**覆盖闸门**。"服务有点慢"只共用"服务"一个泛词，`coverage` 只有 0.25，被拦下。
- `signature ||`：**错误特征命中可以豁免覆盖闸门**——客户贴了报错原文，不需要覆盖率高。
- 最后一条：**整签名命中且带精确标识（错误码、金额）时，分差可以放宽**。客户原样贴了 `-122`，那就是结论性的。

**证据闸门**在召回阶段：

```
lexicalEvidence  = signature || coverage >= 0.15
semanticEvidence = bestSimilarity >= 0.45
```

只有满足其一才进候选池。这条是为"打印机连不上"加的——纯语义路召回的相似度不到 0.45 的，是噪声不是证据。

**未命中时的追问**：`miss` 时返回 `clarify[]`，**按角色生成**：

- 对客户："具体提示的是什么？原文或截图""你登录用的手机号或邮箱""大概什么时候开始的"
- 对运维："生产还是测试环境""影响范围是全部还是个别"

**这条是事故驱动的**：我最初只有运维口径，结果客户收到"是在生产环境还是测试环境？"——这是内部黑话外泄。

#### 6.2.6 闭环：候选 → 审核 → 去重 → 失效

| 阶段 | 实现 |
|---|---|
| 候选 | `kb_propose` 写入 `<kb>/_candidates/<id>.json`，**不自动转正**，不参与检索 |
| 审核 | 人工 CLI：`list / show / verify / reject / expire / stats` |
| 去重 | 新条目的 `errorSignatures` 与现存条目做 **Jaccard ≥ 0.5** → 不新建，只把老条目的出现次数 +1，并返回"已被 X 覆盖" |
| 失效 | `expire(id, {reason, supersededBy})` → `status: deprecated`，保留可查、退出检索；`supersededBy` 指向替代条目 |

出现次数不是纯展示：它作为 `prior` 进打分（见 6.2.4），所以"反复出现的问题排在前面"是自动的。

#### 6.2.7 评测指标

26 条标注用例，四个指标：

| 指标 | 含义 | 目标 |
|---|---|---|
| recall@1 | 第一条是否就是正确答案 | 100% |
| recall@3 | 前三里有没有 | 100% |
| miss-precision | 该判 `miss` 的有没有被判成命中（反之亦然） | 100% |
| tier-agreement | 分级的判断是否和人工标注一致 | 100% |

当前全部 100%。但**这个数字的局限我也说清**：26 条是我自己按现有知识库写的，能证明"调参没把对的弄坏"，不能证明"线上分布覆盖了"。

### 6.3 调参实录（专业版里最值钱的部分）

| 误答 | 表象原因 | 真实原因 | 修法 |
|---|---|---|---|
| "打印机连不上" → 网关 token 变更 | 语义路召回了不相干条目 | 纯向量相似度没有下限 | 证据闸门 `semanticFloor = 0.45` |
| "查看磁盘占用" → PVC 磁盘满 | 后者 `verification` 段写了"磁盘占用回落" | 不分字段权重 / 证据不在该在的地方 | 字段权重 + `signatureTokens` 信号 |

| 客户收到"生产环境还是测试环境" | 追问句只有运维口径 | 角色没参与追问生成 | `missingDetail(query, role)` |
| 模型猜 `service: billing` → 判没找到 | 过滤条件筛空被当成"知识库没有" | 过滤失败应是降级不是否定 | 筛空退回全集 + 明确告知"忽略了该过滤" |

### 6.4 通俗版 ↔ 专业版对照（面试时的心智切换）

| 通俗说法 | 专业说法 |
|---|---|
| 故障卡片 | incident-shaped entry，字段级 schema |
| 按字面找 | BM25 词法召回，块级倒排 |
| 按意思找 | 向量召回（特征哈希 / 兼容 embedding API） |
| 比名次不比分数 | RRF，K=60 |
| 错误特征命中最重要 | `signature` 特征 + `signatureTokens` 特征 + 分块权重 1.5 |
| 只共用一个词不许答 | `directCoverage` 覆盖闸门 |
| 意思不够近不算数 | `semanticFloor` 证据闸门 |
| 敢不敢直接答 | 三级判定 `direct / reference / miss` + `margin` |
| 编不出来就追问 | `miss` → `clarify[]`（按角色生成） |
| 同一个错别重复建卡 | 签名 Jaccard ≥ 0.5 去重 + 出现次数先验 |
| 老方案要下架 | `deprecated` + `supersededBy`，退出检索保留可查 |

## 7. 评测体系

### 7.1 为什么评测

因为这类系统的失败**不是崩溃，是"答得挺像那么回事但是错的"**。

- 答错产品（客户问 A，答成 B）；
- 答得像但编的（知识库里没有，硬给方案）；
- 答对了但语气穿帮（"我先查一下知识库""根据知识库条目 xxx"）；
- 该追问的时候直接下结论。

这四种都不会抛异常、不会 500、日志里一切正常。**没有评测，你改一句 prompt 根本不知道是变好还是变坏。**

### 7.2 怎么评测：两层 + 507 项单测

**第一层 · 12 条端到端**

真实消息打进网关，走完整链路（路由 → 会话 → 模型 → 工具 → 回复），收真实回复。除了看答得对不对，还跑 **6 类泄漏检查**：

| 类别 | 抓什么 | 例子 |
|---|---|---|
| 实现细节 | 框架名、工具名、`token`/`prompt` 这类词 | "每月调用次数或 token 量" |
| 知识库编号 | 条目 id 泄漏 | "根据条目 subscription-fee-9-9…" |
| 检索旁白 | 把内部检索过程说出来 | "我先查一下知识库" |
| 错误承诺 | 承诺做不到的事 | "我帮你查一下" |
| 平台术语 | 插件、预设、扩展、社区 | "这个功能是个插件" |
| URL | 任何链接 | — |

**第二层 · 26 条检索用例**

只看检索层，不看模型。四个指标（见 6.2.7）。这一层的作用是**调参不伤到已有效果**。

**第三层 · 507 项单测**

检索逻辑、网关路由、适配器协议、OCR、知识库导入、审核 CLI、工具输出 schema。

### 7.3 踩的坑（面试必讲）

**坑一：507 项测试全绿，线上全坏。**

检索单测直接调 `search()`，端到端评测只跑"模型的话"，**中间的工具体验层没人测**。所以工具输出格式错了，两层测试都拦不住。

- 表现：客户得到的回复语气完美、内容为零。
- 教训：**测试要穿过真实边界。**"我这一层对"不等于"系统对"。
- 补救：新增驱动真实工具调用 + 按声明 schema 校验返回值的测试，含负向用例。

**坑二：评测脚本自己会骗人。**

脚本里写死了会话 key 的拼法。网关改了 key 之后，12 条全显示"未作答"——而回复其实都在，只是对不上号。

- 教训：**评测工具本身也要有测试**，否则它安静地给你绿灯，比没有评测更危险。
- 补救：改用网关返回的 key，不再自己推导。

**坑三：评测会互相挤压。**

收紧"不要假装去查"之后，"我去查"消失了，但模型改用"token 量"——同一个问题的另一种表现。改一处 prompt 要重跑全部用例，这是必须付的成本。

### 7.4 根据结果怎么修正（每条都能对上具体改动）

| 评测发现 | 改了什么 |
|---|---|
| "我帮你查一下"（做不到的承诺） | 明确禁止 I'll-check 类措辞，只能说"我转给技术同事查一下" |
| "token 量"（实现术语） | 统一成"调用量"，禁用 token/prompt/上下文窗口 |
| 追问问客户"生产环境还是测试环境" | 追问句按角色生成 |
| 模型猜服务名 → 判没找到 | 过滤筛空退回全集，并在结果里说明 |
| "服务有点慢" 直接答了具体方案 | 覆盖闸门 0.30，降级为追问 |
| 客户贴报错原文却只给"参考" | 签名豁免覆盖闸门 |

**这张表的用法**：面试官问"你怎么知道改了以后变好了"，你就指这张表——每一项都有触发它的具体失败，和修完之后的重跑结果。

### 7.5 评测的局限（主动说）

- 12 条端到端是我自己写的，覆盖的是"我想到的场景"。
- 26 条检索用例基于现有 15 条知识库，知识库一换就得重标。
- 泄漏检查是正则，能抓已知句式，抓不住"新的穿帮方式"。
- 没有线上 A/B、没有真实客户满意度数据。

```
          │  └──────┬────────────┬──────┘  │
          └─────────┼────────────┼─────────┘
                    │            │
        ┌───────────▼──┐   ┌─────▼─────────────┐
        │ 知识库        │   │ 运维 Agent         │
        │ 卡片 / 候选   │   │ 独立根会话          │
        │ / 失效三态    │   │ 10min 超时          │
        │ 分块→双路     │   │ 结果转述回客服会话  │
        │ →RRF→三级判定 │   │ 需要人工则通知      │
        └───────────────┘   └───────────────────┘

  控制面板 (Web)：会话列表 · 人工接管 · 备注归档 · QQ 凭证配置
  持久化：每会话一个 jsonl.zstd 追加日志 · key→sessionId 映射 · outbox
```

**四条关键路径**：

1. **正常问答**：客户消息 → 网关 → 会话 → 模型 → `kb_search` → `direct` → 回复。
2. **追问**：`kb_search` 返回 `miss` + `clarify[]` → 模型只问不问不编。
3. **转交运维**：`ops_handoff` → 运维独立会话处理 → 结论回到客服会话 → 客服转述客户。
4. **人工接管**：面板切到 human → 客户消息只入日志不唤醒模型 → 人工直接回复。

## 9. 面试高频追问（速查）

**1. 为什么不用现成的 RAG 框架 / 向量数据库？**
规模只有几十到几千条；要离线可跑（客户环境不一定有外网）；要结果确定性可评测（哈希向量可复现，调参才有意义）。代价我也说得出：默认向量不理解同义词，只能靠 BM25 + 错误特征兜底；换真 embedding 只改配置。

**2. 知识库里没有的问题，怎么防它编？**
三道：三级判定（`miss` 必须追问）、工具描述里明确禁止编方案、评测里有 4 条负例。另外"未命中"时返回的是追问句，不是空结果——空结果会诱导模型自由发挥。

**3. 怎么防止客户看到内部信息？**
工具层按角色摘字段（不是提示词求自觉），`internal` 级别对客服直接报错；再加 6 类泄漏正则做回归。

**4. 多轮上下文怎么管？**
日志只追加，历史是派生的；上下文压缩发生在视图层，不删历史。所以"压缩"和"删除"是两件完全不同的事。

**5. 改了 prompt 怎么保证不变坏？**
12 条端到端 + 6 类泄漏必须重跑。同时诚实说：用例是我写的，能防退化，不能证明覆盖率。

**6. 换成微信要改多少？**
只写适配器。网关只认"渠道 + 用户 + 文本 + 附件"，协议相关的都在适配器里（签名、回复窗口、@ 语法）。

**7. 成本怎么控？**
没命中只追问不生成；检索只取前几名；图片按需识别；上下文压缩；运维转交是异步的，不占客服会话的 token。

**8. 线上出问题怎么查？**
三条证据链：outbox（到底发了什么）、会话日志（模型和工具的真实交互）、适配器日志（有没有送达）。三条一对，就能定位是"没生成""生成了没发""发了没送到"。

**9. 你遇到最难的一个 bug？**
工具输出格式那个。507 项测试全绿、线上全坏，因为测试绕过了真实边界。修复的价值不在补两个字段，而在于加了一条"穿过真实边界"的测试。

**10. 如果重做，会怎么改？**
见第 10 节的前两条。

## 10. 已知局限（主动交代，加分）

1. **默认向量不是真语义。** 特征哈希不理解同义词，"钱少了"和"扣费"在向量空间不接近，靠 BM25 和错误特征字段兜。接真 embedding 的代码路径有，但只验证过"失败降级"分支。
2. **分块是字段级，不是段落级。** 一个很长的 `resolution` 内部没有进一步切分，长条目内部区分度不够。
3. **去重只看错误特征。** 写条目的人写法不统一（"9.9" vs "9.90 元"）就会漏，靠 `signatureSet` 的 Jaccard 兜不住所有变形。
4. **评测集是自建的。** 12 + 26 条，只能证明不退化，不能证明覆盖线上分布。
5. **微信没实现。** 适配器架构支持，但没写；微信个人号协议风险和 QQ 官方 API 完全不同。
6. **写操作没有审批流。** 运维 Agent 现在只能读和转述，扩缩容、改配置这类写操作没有"提议 → 人工批准 → 执行"的链路。
7. **群聊默认一群一条。** 多租户群场景（一群里多个客户）会出现上下文串号，需要显式切成一人一条。
