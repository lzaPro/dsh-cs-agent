1 摘要

1）这份报告接续 重构验收报告（第一批，P1–P14）。第一批解决的是「代码结构撑不住真实使用」：数据库地基、会话状态抽象、回复重投、写入域租约、入站受理、可观测、写入收口、死信重放、数据生命周期、面板拆分、评测门禁、访问控制、发布包自检。本批（P15–P21）解决的是「上线之后真的会咬人的那几件事」：成本算不清、数据该删没人删、能看的人也能删、A 客户的工单能看 B 客户的机器、出事了没人知道、装完不知道能不能用。

一句话总结：第一批把系统做成「能跑、能恢复、能查」，第二批把它做成「能算钱、能合规、能隔离、会喊人、敢交付」。七个阶段全部是"真实使用场景里一定会遇到，但本地开发永远碰不到"的那类问题。

2 第二批七个阶段

七个阶段各自独立提交、各自可回滚、各自带一份 docs/refactor-pN.md。下面按顺序说明每个阶段"真实场景里会怎么坏"和"现在怎么防"。

2.1 成本与用量：写时算，不读时乘（P15）

1）真实问题：老板问"这个月花了多少"，答不上来。消息正文只活在 DSH 会话目录里，token 数从来没落过库。

2）关键约束：单价会变。如果只存 token、查询时再乘当前单价，那么供应商调价之后，历史账单会跟着一起变——这在财务上是不能接受的。所以成本必须在写入时按当时的价格算成整数（micro-USD），读的时候只做加法。

// cs-agent/pricing.js // 价格单位是 USD / 1M token，所以 tokens × (USD/1e6) × 1e6 = tokens × USD // → 结果直接就是 micro-USD 整数，不用浮点、不用四舍五入漂移 export function costMicros(usage, price) { return Math.round( usage.inputTokens * price.input + usage.outputTokens * price.output + (usage.cacheReadTokens ?? 0) * price.cacheRead + (usage.cacheWriteTokens ?? 0) * price.cacheWrite, ) }

3）三个容易写错的地方，都写成了断言：

  • 缓存价缺省按 input 价算——宁可高估。低估会让人以为省钱，高估只会让人来问。
  • 流式回复只计一次——一轮对话可能推 5 个 `assistant/message` 片段，分割计费会把同一批 token 算五遍。
  • `forward: 'all'` 模式只计轮数不计 token——那条路径 token 已经挂在每条消息上了，日报再计一次就是重复。

4）交付：cs-agent/pricing.js、迁移 0006_usage_cost.sql（messages 加 model/provider/cost_micros，usage_daily 加 cost_micros）、GET {route}/usage（每行直接给格式化好的 cost，面板不重复实现换算）、面板「用量」卡、usage-smoke.mjs 48 条（连库 63 条）。

2.2 保留期自动跑：默认关闭（P16）

1）真实问题：P10 做了归档/清除接口，但没人调。合规要的从来不是"有个接口能删"，而是"到期真的会删，且删得有记录"。

2）我最初的实现是默认开启，理由是"合规要的是真的会删"。用户的选择是默认关闭。这个决定是对的：一个会自动删除客户数据的开关，默认必须关着——部署者打开它，等于显式接受了"三天后群聊会话进归档、三十天后进清除"。

这一条记在这里的原因：技术判断（"让合规真的生效"）和产品判断（"删数据的开关不能默认开"）在这件事上冲突，产品判断优先。这类决定不该由实现者替部署者做。

3）打开之后的语义：每 6 小时一轮、启动后先等 60 秒（避免刚起来就删一波）、上一轮没跑完就跳过（不叠加）、租约被接管立刻停表、失败只记 lastError 不进 /health 的失败项（清理失败不该让整个网关判死）。/health.retention 暴露 `lastRunAt` / `lastResult` / `lastError`。

4）交付：resolveRetentionAuto()、runRetentionSweep() / startRetentionWorker()、install() 第四个 effect、面板「自动清理」行、retention-auto-smoke.mjs 44 条。

2.3 只读角色：能看不等于能删（P17）

1）真实问题：P13 加了令牌之后，拿到面板 cookie 的人就能删客户数据、改 QQ 凭证、清空保留期。而真实部署里"给客服主管看一眼会话"和"运维执行清除"根本不是同一批人。

2）权限模型扩成四档，规则刻意简单——新接口默认是"写"：

请求需要理由
GET /healthpublic编排系统探活时还没有令牌
POST {route}inbound适配器投递消息，不是人在操作
GET / HEAD 其余viewer看会话、看死信、看审计
其余（写）admin删除、改配置、重放、执行清除

3）三个细节决定了这套东西好不好用：

  • 401 与 403 分开。换凭证有用 → 401；换凭证也没用（只读令牌）→ 403。混成一个码，前端就没法告诉用户"该换令牌还是该找人要权限"。
  • 只读令牌不回落 admin。它存在的意义就是权限更低。没配 admin 令牌时只告警，绝不把 viewer 提升成 admin。
  • 面板先问角色再渲染。`GET /whoami` 决定按钮画不画 —— 与其让人点了报 403，不如一开始就不给按钮。

4）交付：auth.js 的 viewer 角色与 required()/classify()、cs_view cookie、GET /whoami、面板 6 处守卫、auth-smoke.mjs 70 条。

2.4 账号作用域：工单只看自己的机器（P18）

1）真实问题：ops_handoff 的 account 在重构前只是任务卡上的一行文字。模型写 kubectl get pods -A，就一次扫全集群，输出里混着别的客户的 pod 名和报错，运维照着念给客户就成了泄漏。

2）把这句话变成服务端的硬约束：账号表 → 命名空间白名单 → 与全局白名单取交集（全局写 * 也照样收窄）。三条规则：

  1. 允许本账号命名空间内的操作。
  2. 拒绝不写 namespace 的查询——不写就等于扫全集群。
  3. 拒绝没写账号 / 账号不在表里——不猜，让客服补或让管理员补表。

3）拒绝信息里带该怎么办（"让客服在 ops_handoff 里补 account"），模型不会卡死；ops_env 先把账号和允许的命名空间报出来，模型提前知道边界。ops_env 的 output schema 同步加了 account / scope —— 这里历史上炸过（schema 漏声明导致工具硬错误），所以这条同步本身就是一条断言。

4）交付：ops-agent/scope.js（161 行纯函数）、cluster.js 强制、dispatcher.js 派单绑定、scope-smoke.mjs 58 条。

2.5 指标边界：PromQL 也守这条线（P21）

1）P18 做完之后仍然漏着一个口子：同一张工单还能调 ops_metrics，而它接受任意 PromQL。

-- 这三条都不含"越权"的字面特征，但都在读别人的数据 sum(rate(http_requests_total[5m])) # 没有选择器：跨全部命名空间聚合 {namespace="globex-prod"} rate(errors_total[5m]) # 直接读别人 sum by (namespace) (container_memory_usage) # 一次列出所有客户

2）为什么不解析 PromQL：子查询、by/without、label_replace、二元运算……要做静态判定，等于实现半个求值器，漏掉一种语法就是静默泄漏。选择反过来：不证明查询安全，只接受能一眼看懂边界的写法。

查询形态🟠 拒绝🔵 通过
作用域生效时（工单绑了账号）
没有 namespace 匹配器拒绝：必须显式写—
精确匹配值不在白名单namespace="acme-prod"
正则acme-.*（无法证明不匹配 `acme-secret-project`）namespace=~"acme-prod|acme-staging"
排除式!= / !~（排除一个客户，剩下的仍是所有人）—

3）判定发生在构造请求之前——被拒的查询一个字节都不出网；不是"查回来再过滤"。

4）交付：ops-agent/promql.js（namespaceMatchers / literalAlternatives / checkMetricsScope）、metrics.js 接线（作用域调用时现问，不缓存）、scope-smoke.mjs 58 → 86 条。

2.6 告警：出事了有人知道（P19）

1）真实问题：P6 的 /health 只是"能查"。数据库连不上、租约被接管、回复重试用尽——进程还活着，/health 返回 503，但没人会每分钟去 curl 一次。客户感受到的只是"客服不回话了"。

2）设计上的三个取舍：

  • 复用适配器的 /reply 通道。不引入新的推送系统，告警就是一条发给管理员的消息，与 ops-agent 的 notifyAdmin 同形状。
  • 同一个问题只报一次。新出现报、持续未恢复每小时提醒一次、恢复了发一条"已恢复（持续 N 秒）"。不重复刷屏，也不静默遗忘。
  • 没有配置就整条链关闭。只配了 webhook 没配接收人（或反之）不半开——半开的告警比没有告警更危险。

3）交付：alerts.js（parseAlertConfig / collectIssues / evaluateAlerts / formatAlert / createAlerter）、GET /alerts、/health.alerts、面板健康卡「告警」行、alerts-smoke.mjs 80 条。

2.7 端到端安装：装完真能用（P20）

1）前面有两步检查各自成立：setup-smoke 证明"文件到位"，check-plugin-apply 证明"apply() 不抛"。但两者之间的缝——路径没走 defaultPaths()、凭证没读到、知识库目录是空的、路由前缀写错——从来没有一条测试穿过。

2）scripts/install-e2e-smoke.mjs 从空 DSH_HOME 按 INSTALL.md 装一遍（并且从别的目录执行，因为用户不会在包目录里跑），然后让真插件代码在那个 home 上跑起来，走完七组断言：

  1. 装完之后 paths.js 解析出的 root 就是那个临时 home，六个子目录都在，kb/ 不是空目录。
  2. kb_search 命中自带的 example-disk-full 且判定为 direct。
  3. /config 读到安装脚本写的 AppID、不回传 secret、envFile 指向装好的那份。
  4. 新装默认无令牌并在日志里明确告警；面板 HTML 打开、/health 200。
  5. 一条客户消息 → 假适配器收到回复 → outbox 留底 → /history 可查。
  6. 关停重启后同一客户拿回同一个 session，/sessions 只有一条。
  7. 全程写入都在装好的 home 里，凭证文件保持 0600。
为什么"从别的目录执行"是一条断言而不是细节：在包目录里跑，process.cwd() 会成为隐式的路径来源，测试会绿；而用户机器上不是这么用的。同理，DSH_HOME 是在装完之后才设的——如果一开始就设好，"安装脚本写到了 A、插件读的是 B"这种事故会被完美掩盖。

3）交付：scripts/install-e2e-smoke.mjs（330 行 / 48 条）、verify-all.sh 加 == install e2e。

5 这批抓出的问题

报告第一部分列了 13 个被测试抓出的真 bug。本批又抓到一批，分三类记，因为它们的性质不同。

5.1 真 bug 与真漏洞

#问题后果与修法
1 告警发送不检查 response.ok 适配器返回 503 时 fetch 不抛，告警被记成"已发送"、lastError 被清空、下一轮不再重报。告警在最需要它的时候静默失效。修法：与 postReply 一致，非 2xx 抛错。
2 ops_metrics 不受账号作用域约束 P18 把 k8s 堵住了，但一条 sum(rate(...)) 或 {namespace="globex-prod"} 照样越界。指标看起来不像数据，念给错的客户也不会有人察觉。修法：P21 的 PromQL 边界。
3 retentionAuto 我实现成默认开启 会自动删除客户数据。用户改成默认关闭——部署者必须显式打开。这是我判断错了，不是代码写错了。

5.2 我自己做反的决定

第 3 条（保留期默认开启）值得单列。当时的推理是"合规要的不是接口，是真的会删"，这在技术上成立；但默认值是一种承诺——默认开启等于替所有部署者承诺"你同意三天后归档、三十天后清除"。这类决定的权利在部署者手上，不在实现者手上。

5.3 接口没有单一真源的代价

P20 写端到端测试时，三个"我的测试写错了"的失败，两次都指向同一个结构问题：

  • kbStore.stats() 与 search() 的形状不一致。我按 search(query, role) 的形状写成 stats('customer-service')，返回里没有 total 字段。实际签名是 async stats()，返回 {shared, internal, candidates, ...}。只能靠读实现才知道。
  • scopeFor(accounts, raw) 的第一个参数是 parseAccounts() 的结果。直接传原始配置对象得到 {configured: false}，于是"该拒绝"的断言全过不了、"该通过"的也过不了。parseAccounts 的返回形状是 scopeFor 的隐含契约，类型上没有任何约束。
  • ops_metrics 的输出 schema 是封闭的（additionalProperties: false），所以作用域检查只能抛错、不能塞一个 scope 字段回去。这是对的设计，但要求实现者清楚"错误路径"与"结果路径"的分界。
这不是测试的问题，是接口的问题：形状不一致、隐含契约、错误路径与结果路径混用——三者都会让下一个人（或下一个 AI）多花半小时读实现。本批把这三条都写进了各自的 docs/refactor-pN.md，算是补了一层文档真源，但没有从代码层面消除。

6 已知边界

1）真实 QQ 适配器没有被端到端覆盖。假适配器只验"网关发出的 HTTP 载荷对不对"，不验重投频率与消息 id 稳定性。

2）没有起真的 dsh 进程。P20 自己 apply() 再跑 disposer，等价于插件生命周期，但不是真实销毁顺序，也没有覆盖多实例。

3）指标边界只认 namespace 一个标签。客户边界若体现在 cluster / tenant / service，需要显式扩展（有意写死，多认一个标签就多一份误判）。

4）多租户仍然没有。当前边界是"账号 → 命名空间"，不是"租户 → 全部数据"。表结构里预留了 tenant_id，但没有实现。

5）保留期没有按客户粒度删除的自动化（手动 /retention {owner} 有）。

6）`ops_env` 不报指标作用域。模型要靠 P21 的错误信息才知道 PromQL 也要写 namespace —— 可以提前到开工提示里，本轮没做。
