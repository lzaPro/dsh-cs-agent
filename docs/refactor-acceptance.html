客服 Agent 插件重构验收报告
2026-10-27 | v1.0

1 摘要

1）这轮改造的目标不是"代码更漂亮"，而是让这套客服插件能承接真实的客服流量。重构前它是一套能跑通演示的骨架：消息能进来、模型能回、面板能看，但几乎所有"真实系统该有"的保障都缺——消息会因为一次图片下载超时丢掉，回复会因为适配器抖一下永久不发，出了事没有任何 id 能把一条消息串起来，删客户数据没有任何手段。

2）十四个阶段全部提交，每个阶段都配一套可复跑的验收。基线是一条命令跑 21 步、507 条断言；现在是 36 步、942 条断言（不连库）/ 1091 条（连库），全部通过。

一句话结论：重构把"消息不丢、回复不重、故障可追、数据可管、发布可验"这五件事从"没做"变成了"有代码、有测试、有文档、能回滚"。剩下没做的是成本核算与发布管理，以及若干规模上限。

1.3 一句提醒

关于"结构变好了吗"：gateway.js 从 1779 行涨到 1952 行。拆走了 519 行面板，但又装进了投递队列、受理队列、健康检查、审计、保留期、消息归档这些新能力——它们天然属于"这个网关"。这轮我优先保证能落地，可读性上只做了面板拆分这一刀。真要继续瘦身，下一步是把 21 条 HTTP 路由拆成独立路由模块（见 9 节）。

2 出发点：重构前的真实故障

1）下面每一条都不是"代码风格问题"，而是能造成客户损失或数据事故的具体缺陷。它们是我读 cs-agent/gateway.js 1779 行后逐条定位的，后面每个阶段都对着其中一到两条。

#现象代码位置（重构前）后果
1 入站消息会因为一次临时故障永久丢失 gateway.js:522-593 的 inbound()：去重、限流、下载附件、建/恢复会话、落盘、唤醒模型、记去重窗口，全在一个同步函数里 4 张截图中第 3 张 AbortSignal.timeout(8000) 超时 → 整条消息抛错；适配器不重投 → 客户以为发了，客服从没看到
2 回复失败没有任何重试 gateway.js:596-637 的 emit()：先 appendFile 写 jsonl，再单次 fetch；失败只 warn 后返回 {delivered:false} 适配器重启 3 秒 → 模型答的话永久丢；jsonl 里躺着"发过"的记录，但客户没收到
3 会话状态是内存 Map + 整份文件重写 gateway.js:222-233 的 persist() / persistSeen()：每条消息都把全部会话（去重窗口 2000 条）全量重写一遍 无写队列、无节流；并发写会互相覆盖；会话上万时每次提问都要重写整份文件
4 只能单进程单机 gateway.js:64-91 的 acquireDataLock()：<data>.lock 写 PID，第二个进程直接拒绝启动 无法扩容、无法滚动发布；机器崩了锁文件（PID 被复用）可能挡住重启
5 初始化有竞态 gateway.js:204-220 的 load()：先置 loaded = true，再 await 读文件 两条消息并发首次到达 → 第二个调用看到 loaded 已真但数据还没读完 → 重复建会话
6 出了事串不起来 全文件没有 traceId；日志是裸文本 客户报"晚上 8 点那条没回"，只能翻日志按时间猜是哪条、走到哪一步
7 鉴权只对了一半 gateway.js:1485-1488：if (token !== undefined) 才校验 Bearer 头 配了令牌 → 浏览器打不开面板（浏览器不给页面请求加 Authorization）；不配令牌 → /delete、/config（改 QQ 凭证）、/retention（删客户数据）全部匿名可调
8 删除客户数据没有手段 scripts/retention.mjs 只处理运行时目录的 json 文件 客户要求删除时做不到；合规上是硬伤
判断：这 8 条里有 5 条是"故障发生时数据会丢或会重复"——这是客服系统最不能忍的一类错。所以重构顺序不是"先把代码拆干净"，而是先补可靠性，再补可观测，最后补运营手段。

3.1 三个阶段值得单独讲

1）P5 是最能说明"为什么顺序是这样"的一个阶段。入站受理的改造看起来只是"加个队列"，但它迫使一个原本模糊的问题变清楚：同一条平台消息重投两次，怎么认出来是同一件事？第一版实现把整个信封（含 at 时间戳）哈希成幂等键——同一 messageId 每次重投算出的键都不一样，于是队列里排两条、客户收到两条一模一样的回复。这个 bug 是写代码时自己发现的，不是测试抓的；修法是把幂等键从"信封内容"改成"平台消息 id / 内容指纹"。

2）P7 暴露了一个隐藏的进程级隐患。给 emit() 加上"租约丢了就抛错"之后，observe() 里那三处 void emit(...) 立刻变成无人接管的 Promise rejection——Node 15 之后默认直接终止进程。也就是说：租约被接管的那一刻，整个网关会崩。修法是引入 trackReply() 统一收集在飞回复（顺带解决了"测试/优雅关停无法等待回复落定"的问题）。

3）P12 把"评测"从分数变成证据。原来的 eval-rag.mjs --strict 只回答"recall@1 是不是 100%"，改坏一条要自己一条条 diff 输出才能找到。门禁改成与基线逐条比对：基线里 hit1:true 的用例现在不中了，就直接报 case X used to hit "Y" and now returns "Z"。同时它会校验用例引用的知识条目真实存在——否则条目改名后门禁会静默失效，变成永远绿。

5 可选性：不启数据库，行为一行不变

1）这是整轮改造最重要的工程约束。四个包原本零运行时依赖，装完就能跑；如果一上来强制 PostgreSQL，安装门槛会从"拷目录"变成"先会运维数据库"，现有部署全炸。所以每一项新能力都做成开关 + 双实现。

packaging-smoke.mjs77四个包 npm pack 真实清单：凭证不外发、每个 exports 目标在包里、真装一次并 import 每个入口

6.3 门禁设计要点

1）断言优先于快照。会话状态这类结构用"契约测试"（contract(store, label)）而不是黄金文件——两套实现必须对同一份断言全绿，结构变动不会造成无意义的重写。

2）gateway-smoke 那 109 条一条都没改。它是纯回归门禁：每加一个能力，这 109 条必须原封不动全绿。整个重构期间每次都是 109 PASS。

3）检查必须能挂。每个测试写完都做过反向验证：故意改坏一处，确认它报错并指出具体位置。例如把 files[] 里的 time.js 删掉，packaging-smoke 立刻报 4 条失败并点名"找不到 time.js"。

6.4 测试与实现过程中抓到的真 bug

1）这些都不是"测试写错了"，是产品代码里真实存在的缺陷，靠新增的验收手段暴露出来。我认为这是这轮改造最有说服力的部分。

#阶段缺陷修法
1P2load() 先置 loaded=true 再 await；并发首调读空 → 重复建会话先 await store.load()，成功后再置标志

7.1 三种部署形态

7.2 起库与迁移

# 起库（默认 55432 端口，避开常见的 5432 冲突） ./scripts/db-up.sh # 只用本次会话、不写 .env.db： DSH_DB_IMAGE=postgres:18-alpine ./scripts/db-up.sh # 停库（保数据）/ 连数据一起清 ./scripts/db-down.sh ./scripts/db-down.sh --purge # 看迁移状态（不应用） DSH_DB=1 node cs-agent/db/migrate.mjs --status

1）db-up.sh 会做五件事：校验 docker、检查端口占用、docker compose up -d、轮询容器健康（最多 60s）、按需 npm install --no-save pg 并执行迁移。

2）迁移器会记录每个文件的 sha256。已应用过的迁移文件被改动会直接报错，要求"加一个新迁移而不是改历史"。这是刻意的：改历史会让不同环境悄悄产生不同的表结构。

7.5 运维面板

1）/panel 是三栏结构：左边会话列表（搜索、按人工/机器人过滤、批量归档），中间对话与回复，右上角「运维」按钮进入四张卡片：

  1. 健康 是否 ok、运行时长、存储与租约类型、两个队列积压、数据库版本、失败的检查项
  2. 死信 inbox / outbox 分区，显示正文预览、试了几次、最后错误；单条「重放」与「全部重放」
  3. 数据保留 先看计划（干跑），有计划才出现「执行」按钮，confirm 二次确认
  4. 审计 最近 20 条操作来源与动作
面板没有登录态以外的权限分级：能打开面板就能删数据。所以不要把它暴露到公网，只放在内网或 SSH 隧道后面。这一点写进了 INSTALL.md 与 docs/refactor-p11.md。

8 关键设计决策与理由

1）下面每条都是"本来可以走另一条路"的地方，写清为什么不走。

#决策理由与代价
1 数据库可选，不是前提 四个包原本零依赖、装完就能跑。强制 PostgreSQL 会把安装门槛从"拷目录"变成"会运维数据库"，现有部署全炸。代价：每项能力要维护两套实现，测试跑两遍（942 / 1091 条）
2 知识条目正文不进库 人工审核、diff、回滚、reviewer 签字都依赖 git。数据库只装业务状态。代价：跨库 join 做不了（但按条目 id 关联足够）
3 新能力开关只认显式配置 DSH_CS_STORE 与 DSH_DB 分开：DSH_DB=1 只表示"数据库能力可用"，不该顺手改变会话存在哪儿。否则开发者 export DSH_DB=1 后跑 verify-all，gateway-smoke 会意外连库
4 投递队列只在配了 webhook 时启用 没配 webhook 的部署（比如只做存档）不该凭空多出一套队列和状态文件。这条让 gateway-smoke 那 109 条断言逐字节不变
5 幂等键从内容派生，不用随机 UUID 平台会重投同一条消息；随机键会让每次重投都变成一条新记录。代价：同一秒内两条措辞完全相同的消息会被当成一条（可接受，比重复回复好）
6 丢锁后立刻停写（503），不降级 租约被接管说明另一个实例在写。继续写会导致两实例同时唤醒模型、客户收两条、会话映射被覆盖成失效 session——全都不报错。宁可显式失败
7 审计双写（jsonl + 表） 表是查询索引，jsonl 是"数据库挂了也能查"的底稿。两处都失败只 warn——操作已经生效，回滚更糟
8 audit_log / ticket_events 用数据库触发器做 append-only 用权限控制需要额外的角色体系；触发器 + set local app.allow_purge='on' 这一个逃生舱口，既能保证不可改，又能让测试/合规清理走明路
9 评测门禁逐条比基线，不比总分 "recall 88% vs 90%" 定位不到问题；"用例 X 以前命中 Y、现在返回 Z" 直接指到知识条目。同时校验用例引用的条目真实存在，否则改名后门禁静默失效
10 发布包检查问 npm，不自己复刻规则 npm 的 files[] / .npmignore / 总是包含项的规则细节多且会变；复刻一份等于制造第二个真源。代价：检查依赖 npm 可用
11 面板渲染不用框架，仍是一段内联脚本 零依赖是这套插件的卖点，为了一个内网面板引入构建链不值。代价是模板字符串里的反斜杠要写两层（P11 那个 SyntaxError 就是这么来的，现已加检查）
12 每个阶段一个提交 + 一份文档 目的是可单独回滚。任一处出问题，git revert 一个提交就退回上一个可用状态，不需要理解整套改造

9 还没做的，以及已知风险

9.1 明确没做

缺什么现状影响与建议
成本核算 usage_daily 记了轮数与 token（含缓存读写），但没有单价，算不出钱 要回答"这个月花了多少"，需要配置单价表（按模型分）。这是下一个最该做的（P15）
保留期自动跑 端点有了、纯函数有了，但没有内置定时器，要外部 cron 调 POST /retention 真实部署必须配一个 cron，否则保留期只是"能执行"而不是"在执行"
多租户 只预留了 tenant_id / account_id 列，没有隔离逻辑 SaaS 化才需要。当前"按客户删除"已按 key/senderId/groupId 支持，够单一组织用
告警接线 /health 可被采集，但没有 Prometheus exporter / webhook 告警 队列积压、死信增长这些指标现在只能人肉看面板。接线是运维侧工作，接口已具备
面板权限分级 有 admin / inbound 两角色，但面板内"能看"与"能删"不分离 多客服场景下需要"只读客服"角色。当前建议面板只在内网
发布管理 prompt / 知识库没有版本化与灰度；改 prompt 就是改代码 多人协作后才痛。当前靠 git 版本 + 评测门禁兜底
端到端安装测试 packaging-smoke 验到"装出来的文件能 import"，但没验"从 tarball 装 → 起网关 → 发一条消息" 真正的发布前验收。要起 DSH 环境，成本较高
路由拆分 gateway.js 里 21 条路由还是一个 if 链 可读性问题，不影响正确性。要拆的话建议按"面板 / 队列 / 运营 / 入站"四组

9.2 已知风险

1）单机文件模式仍是单进程。靠文件租约保证，两个进程共用同一数据目录会被拒（第二个启动失败）。要多实例必须切 DSH_CS_STORE=postgres。这是设计如此，不是残留缺陷。

2）pg 是 optionalDependency。忘了 npm install 时不会在启动报错，只在真正启用数据库时报 database driver "pg" is missing。这是"零依赖可跑"的代价。

3）json 模式的 listMessages 整份读文件。会话上万条时会慢。切数据库即解决；文件模式定位是"小规模/单机自用"。

4）入站重试可能重复归档消息。messages_platform_msg_uniq 部分唯一索引会挡住重复行，但会留一条 warn 日志噪音。不影响正确性。

5）迁移文件不可变。已应用的迁移被改动会报错——这是保护，但如果有人不熟悉，会觉得"改不了一行 SQL"。规则是加新迁移文件。

如果要我给一句最实在的建议：下一步先把 P15 成本核算和保留期定时器补上——这两件事不做，"能落地"就还差最后一公里：老板问"这个月花了多少"答不出来，合规问"数据删了吗"只能答"接口有了但没人调"。
